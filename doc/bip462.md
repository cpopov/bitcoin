# BIP 462 reference implementation: target-based demurrage

This branch is a reference implementation of
[BIP 462 (draft 0.6.0), *Target-Based Demurrage Security Budget*](https://github.com/cpopov/bips/blob/demurrage-security-budget/bip-0462.md).
It is a **hard fork**. It is not scheduled on any network: mainnet, testnet and
signet have no activation height. On regtest it activates only with
`-testactivationheight=demurrage@<height>`.

Since draft 0.5.0 (fees go to the block producer and do not count towards the
target; reference heights are inherited, see
[the design review](bip462-design-review.md)), draft 0.6.0 adds:

- **A rate per block.** `r(h)` covers the shortfall between the target and the
  subsidy of block `h` itself. There are no rate periods.
- **An index floor.** Once the index is at or below `INDEX_MIN`, the rate is
  zero, so the index never reaches zero.
- **Timestamp rules.** The two timestamp rules of BIP 54 apply from activation.
- **An activation block.** The block at `ACTIVATION_HEIGHT` sets bit 31 of its
  header version.
- **A demurrage commitment** in every coinbase from activation.
- **`SIGHASH_DEMURRAGE`**, an optional taproot signature hash flag.

[What is not implemented](#not-implemented) lists the parts of the draft that
this branch does not cover.

## Trying it on regtest

```bash
bitcoind -regtest -testactivationheight=demurrage@432 -daemon
bitcoin-cli -regtest createwallet w
bitcoin-cli -regtest -generate 600
bitcoin-cli -regtest getdemurrageinfo
```

Regtest uses a target of 1/500 per block (0.2% per block, far above mainnet's
0.3% per year). That way demurrage is non-zero while regtest's fast-halving
subsidy (every 150 blocks) still exists. Its difficulty adjustment period, to
which the timestamp rules apply, is 144 blocks.

## How it works

1. **Fixed point.** I(h) and r(h) are integers scaled by 10^18. Every
   operation rounds down:
   - `I(h) = floor(I(h-1) * (10^18 - r(h)) / 10^18)`, with I(h) = 10^18 for
     every h below activation;
   - `r(h) = floor(max(0, target - block_subsidy(h)) * 10^18 / U)`, with
     `target = floor(U * 3 / 52,560,000)` and `U = U(h-1)`;
   - `r(h) = 0` if `U = 0`, or if `I(h-1) <= INDEX_MIN = 10^9`: the index
     stops falling there, so it never reaches zero;
   - `effective = floor(v * I(at) / I_created)`;
   - `dividend = floor(r * U / 10^18)`.

   On mainnet the target rate is 57,077,625,570 (≈ 5.7078e-8 per block). The
   rate of the first block after a halving already covers the new shortfall.
2. **Reference heights.** A coinbase output's reference height is its
   block's height. Any other output's reference height is its transaction's:
   the highest reference height among the outputs it spends. Inputs are
   valued at `I(ref_height)`, and outputs are created with
   `I_created = I(ref_height)`.
   - A transaction with one input is always valued at its nominal value.
   - A transaction spending only outputs created before activation is valued
     at index 1, however long it waits.
   - A transaction's validity no longer depends on its inclusion height, except
     through reorganisations at least 100 blocks deep, since every reference
     height descends from a mature coinbase.
3. **U(h), the effective value of the UTXO set.** The implementation tracks
   the exact integer `N = sum(floor(v * 10^36 / I_created))` over all
   unspent outputs, adding and removing outputs as blocks connect, and defines
   `U(h) = floor(N * I(h) / 10^36)`. At `ACTIVATION_HEIGHT - 1` every output has
   index 1, so `N` is the UTXO set's total value × 10^18. The node does not
   wait for that block to compute it. It scans the UTXO set once, at a height
   it picks at random between 2,016 and 1,008 blocks before
   `ACTIVATION_HEIGHT - 1`, so that nodes do not all scan at the same block.
   From then on `ConnectBlock` adds the outputs each block creates and
   subtracts those it spends. A node that starts later, for example one
   upgraded after its height was passed, scans at the next block it connects,
   and at the latest at `ACTIVATION_HEIGHT - 1`.
4. **Coinbase limit:** `subsidy + sum(fee_effective) + dividend`, where
   `fee_effective = floor(fee * I(h) / I(ref_height))` converts each fee from
   its transaction's reference height to the block's. Any unclaimed amount is
   destroyed.
5. **Block headers.** From activation, the first block of a difficulty
   adjustment period is at most 7,200 seconds earlier than its parent, and the
   last block of a period is not earlier than its first (reject reason
   `time-timewarp-attack`). The block at `ACTIVATION_HEIGHT` sets bit 31 of its
   version (`bad-version` otherwise), and the rule that rejects versions below 4
   does not apply to it, so no other block can set the bit. Both checks run
   when a header is accepted and again when its block is connected, because a
   node upgraded after activation accepted headers without them.
6. **Demurrage commitment.** Each coinbase from activation has an output
   `OP_RETURN <0x9996b0b3 || commitment>`, with `commitment = SHA256d(I(h) ||
   r(h) || N(h-1) || ref_height_root)`. `ref_height_root` is the Merkle root
   of `SHA256d(txid || reference height)` over the block's transactions, with
   32 zero bytes and the block's height for the coinbase. Reference heights
   below activation are committed as `ACTIVATION_HEIGHT - 1`, whatever height
   the coin records. The last matching output counts
   (`bad-demurrage-commitment-missing`, `bad-demurrage-commitment`). Block
   templates carry the output, and `getblocktemplate` reports it as
   `default_demurrage_commitment`.
7. **`SIGHASH_DEMURRAGE` (0x40).** From activation, taproot key path and script
   path signatures may use hash types 0x41, 0x42 and 0x43. The signature
   message then also holds the SHA256 of the value of every input at the
   transaction's reference height, and that height in committed form. The flag
   has no script verification flag of its own: it is valid where validation
   supplies those values (`PrecomputedTransactionData::SetDemurrage`), which it
   does for every transaction of a block at or above activation, and for the
   mempool once the next block is. The script execution cache key includes
   them, since the witness hash does not determine them. Legacy and BIP 143
   signature hashes are unchanged.
8. **Signing with `SIGHASH_DEMURRAGE`.** `walletprocesspsbt`,
   `descriptorprocesspsbt` and `signrawtransactionwithwallet` accept the hash
   types `ALL|DEMURRAGE`, `NONE|DEMURRAGE` and `SINGLE|DEMURRAGE`. They sign
   taproot inputs with the flag and other inputs without it, since it is for
   taproot only. The signer needs the value of every input at the
   transaction's reference height:
   - **PSBTs** carry it in two input fields. The BIP leaves their key types
     unassigned, so they are proprietary keys (`0xFC`) with identifier
     `bip462` and no key data: subtype `0x00` holds the reference height of
     the output spent, in committed form (4 bytes, little-endian), and subtype
     `0x01` the input's value at the transaction's reference height (8 bytes,
     little-endian). The wallet (`FillPSBT`, so `walletcreatefundedpsbt`,
     `walletprocesspsbt`, `send` and `psbtbumpfee`) and the node
     (`utxoupdatepsbt`, `descriptorprocesspsbt`) record them once BIP 462
     applies to the next block and the coins are known, replacing any fields
     already there. `decodepsbt` shows them under `demurrage`.
   - **A signer that does not know the coins** uses the fields as they are.
     It refuses them if an input would be worth more than its nominal value,
     or if an input at the transaction's reference height would be worth less
     (`GetDemurrageSigningData`). Wrong values that pass these checks give an
     invalid signature, so a valid signature pays the fee the fields give.
     `decodepsbt` and `analyzepsbt` compute the fee from the fields when the
     node cannot value the inputs itself.
   - **Raw transactions** (`signrawtransactionwithwallet`): the wallet values
     the inputs itself.

   Without the values, signing with these hash types fails with an error
   that says so. The wallet's own transactions (`send`, `sendtoaddress`, ...)
   are signed with `SIGHASH_DEFAULT` unless `-walletdemurragesighash` is set
   (see Replay protection below).
9. **Coin and undo formats.** Coins created before activation, and coinbase
   outputs, keep the existing serialization. A coin whose reference height
   differs from its height sets bit 32 of its serialized code, followed by
   `VARINT(height - ref_height)`. Undo records keep the delta in the slot that
   old versions used for a transaction version. Existing UTXO sets and undo
   files stay valid.
10. **UTXO set hash.** `hash_serialized_3` and MuHash (`gettxoutsetinfo`, the
   coinstats index, assumeutxo) commit to a coin's reference height when it
   differs from its height: bit 31 of the hashed code is set, and the
   reference height follows as 4 bytes. Heights below 2^30 leave that bit
   clear, so every UTXO set before activation, and every existing assumeutxo
   hash, is unchanged. The coinstats index takes each transaction's reference
   height from the block's undo data, so it hashes the same coins as a scan
   of the UTXO set. Nominal amounts no longer balance once a dividend is
   claimed, so its `unclaimed_rewards` is the coinbase limit less what the
   coinbase claims.
11. **Rounding.** Effective supply grows by the subsidy minus a few satoshis
   per block (at most about one per input and per transaction). The
   functional test checks this bound on every block.

## Policy, mining and wallet

- **Relay is unchanged.** Any transaction version, including TRUC, is relayed
  as before. A zero-fee TRUC commitment and its anchor child relay after
  activation, and TRUC still rejects oversized pinning children.
- **Mempool fees.** A fee is expressed at its transaction's reference height,
  so the fees of two transactions are not directly comparable. When a
  transaction enters the mempool, its fee is converted once to `fee_effective`
  in the next block (`MemPoolAccept::PreChecks`). That is the fee the mempool
  ranks, compares for replacements, checks against the minimum relay fee and
  reports (`getmempoolentry`, `testmempoolaccept`). The BIP suggests the fee at
  index 1.0 for comparisons. The two differ only by the demurrage that accrues
  while a transaction waits, and `fee_effective` is in the unit of the
  thresholds. Block templates recompute each fee exactly for their block
  (`GetDemurrageBlockFees`), and `getblocktemplate` reports those fees, the
  coinbase value and the demurrage commitment.
- **Reorganisations** re-check input values against the new chain. A
  transaction whose witness may hold a `SIGHASH_DEMURRAGE` signature has its
  scripts verified again too, since such a signature commits to those values
  and is invalid below activation (`MaybeUpdateMempoolForReorg`).
- **The wallet** values coins at their effective value at its last processed
  block, looked up through the node (`findCoins`), and reports effective
  balances (`getbalance`, `getbalances`, `listunspent`). After selecting
  coins, it re-expresses the transaction's outputs at the transaction's
  reference height (`ConvertOutputsToRefHeight`), so that each recipient
  receives the requested effective amount and the fee is as intended.
  The mempool measures the fee one block later, so the wallet takes the few
  satoshis of difference, and of rounding, from the change. `sendall` does
  the same, with its inputs, including any passed in `inputs`, valued at their
  effective value.
- **Fee bumps.** `bumpfee` and `psbtbumpfee` keep the amount of every output
  they do not replace. Those amounts are nominal at the original
  transaction's reference height, so they are unchanged unless the
  replacement adds a younger input, which re-expresses them at the new
  reference height: the effective value delivered is the same. The original
  fee and the new fee are reported as consensus computes them, with the inputs
  valued at each transaction's reference height.
- **Unbroadcast wallet transactions.** Coins of wallet transactions that are
  neither confirmed nor in the mempool (for example with `-walletbroadcast=0`)
  are valued too: their reference height is derived from the coins their
  transaction spends, following unbroadcast wallet parents if needed. As
  before BIP 462, external inputs must be in the UTXO set or the mempool.
- **Replay protection** (the BIP's "Chain split and replay") is opt-in, with
  `-walletdemurragesighash` (off by default). Once BIP 462 applies to the next
  block, the wallet then signs the transactions it sends (`sendtoaddress`,
  `sendmany`, `send`, `sendall`, `bumpfee` and the GUI) with `ALL|DEMURRAGE`
  (`CWallet::GetOwnTransactionSighash`). A transaction with a taproot input is
  then invalid on a chain that does not apply BIP 462, and spending a coin
  with it separates that coin from the other chain.
  - Other inputs are signed with `SIGHASH_ALL`, since the flag is for taproot
    only. A transaction without a taproot input is protected only if it spends
    a separated coin, one that the other chain does not have. The wallet counts
    two kinds as separated (`COutput::separated`, set by `AvailableCoins`):
    - coins descended from a coinbase mined at or after activation, the BIP's
      other separation, whose reference height is at or above
      `ACTIVATION_HEIGHT`;
    - outputs of a transaction with a `SIGHASH_DEMURRAGE` signature, and of the
      transactions that descend from one through the wallet's own
      (`TxDescendsFromDemurrageSignature` in `src/wallet/receive.cpp`). Only
      a taproot input spent by the key path counts: its witness has a single
      element (besides an annex), a 65-byte signature whose hash type has the
      flag. The scripts of the spent outputs come from the block's undo data
      or the mempool (`getDemurrageInputValues`, cached with the wallet's
      debit), so a transaction from another wallet counts too.
  - Coin selection therefore prefers an input set with a coin that protects
    the transaction (`AttemptProtectedSelection`): a taproot coin or a
    separated coin. For each output type that has one, it takes the best set
    of that type if that set includes such a coin. Otherwise it takes the coin
    (or address group) of that type with the largest amount and selects other
    coins of the type to make up the rest. It keeps the set among these that
    wastes the least, so a wallet that has both kinds spends whichever costs
    less.
  - If no single type will do and mixing output types is allowed, it tries
    the best mixed set, if that set includes such a coin. Failing that, it
    takes the largest such coin, and coins of any type for the rest.
  - It looks for such a set under each coin eligibility filter in turn before
    the usual selection. It therefore spends a protecting coin with one
    confirmation rather than a better-confirmed coin that does not protect.
    It may pay more fees than the set it would otherwise pick.
  - A preselected input that protects the transaction is enough: one of the
    wallet's taproot coins, a separated coin of the wallet's, or any coin,
    the wallet's or external, descended from a post-activation coinbase. A
    wallet without private keys, including one with an external signer, only
    prefers separated coins. A wallet with neither kind of coin selects as
    usual.
  - The preference applies to every transaction the wallet funds once BIP 462
    applies, including those of `fundrawtransaction` and
    `walletcreatefundedpsbt`, which are signed separately.
  - Before activation, and when the wallet cannot value every input (an
    external input passed to `send`), it signs with `SIGHASH_DEFAULT`.
  - The size estimate already allowed for a hash type byte on taproot
    signatures, so the fee rate is the one requested.
  - PSBT signing (`walletprocesspsbt`) and `signrawtransactionwithwallet`
    keep the hash type they are given, and external signers their own.

## Reporting

Nominal fields keep their meaning, and effective values are added beside them,
as in `gettxout`, once BIP 462 applies:

- `gettxoutsetinfo`: `effective_total_amount`, U(height) from the block's
  demurrage state, with or without the coinstats index.
- `scantxoutset`: `ref_height` and `effective_value` of each output, and
  `effective_total_amount`.
- REST `getutxos` (JSON): `ref_height` and `effective_value` of each output.
  The binary and hex formats are unchanged.
- `gettransaction`, `listtransactions` and `listsinceblock`: the transaction's
  `ref_height`, with its amounts and fee expressed at that height and its
  inputs valued as consensus values them. The node reads the spent coins from
  the block's undo data, or from the UTXO set and the mempool if the
  transaction is unconfirmed.
- `decodepsbt` and `analyzepsbt`: the fee with the inputs valued at the
  transaction's reference height, looked up in the UTXO set and the mempool.
- `listaddressgroupings`, `getreceivedbyaddress`, `getreceivedbylabel`,
  `listreceivedbyaddress` and `listreceivedbylabel`: effective values at the
  wallet's last processed block, like balances. An amount received is valued
  from its transaction's reference height, whether or not the output is still
  unspent, so it declines over time as a balance does.

## Upgrading, assumeutxo and Layer 2

- **Upgrading after activation.** A node without BIP 462 rejects the
  activation block, and can only have followed blocks that do not set the
  activation bit. At startup, a chainstate whose tip is at or above
  `ACTIVATION_HEIGHT` without a demurrage state disconnects back to
  `ACTIVATION_HEIGHT - 1`. Activating the best chain then validates the blocks
  again under BIP 462 rules. The block the node had at `ACTIVATION_HEIGHT`
  fails them, so it is marked invalid with its descendants, and the node
  follows the chain that applies BIP 462 once it receives it. Should a block
  be connected again with undo data written without reference heights, that
  undo data is replaced (`BlockManager::WriteBlockUndo`).
- **assumeutxo.** A snapshot whose base is at or above `ACTIVATION_HEIGHT`
  uses format version 3, which adds the demurrage state after each block from
  `ACTIVATION_HEIGHT - 1` to the base. The assumeutxo data commits to their
  hash (`demurrage_states_hash`, reported by `dumptxoutset`), and loading checks
  that the coins add up to the base block's normalized UTXO total. Background
  validation computes the states again, including the UTXO set value at
  `ACTIVATION_HEIGHT - 1`, and checks their hash before declaring the snapshot
  valid. Snapshots below activation keep version 2.
- **Layer 2.** The functional test checks the consensus behaviour that BIP
  462's Layer 2 section relies on: a commitment and a second-stage
  transaction signed long before they are broadcast stay valid at their
  nominal amounts, outputs inherit the funding output's reference height,
  zero-fee TRUC commitments with anchors relay, and a younger input added to a
  `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` transaction raises its reference
  height and must pay the decay of the pre-signed input.

## Not implemented

- **Replay protection without a protecting coin.** A transaction is not
  protected if the wallet has no coin to spend that protects it: neither a
  taproot coin that it signs nor a separated coin. Nor is it protected if its
  preselected inputs pay for it without one. The wallet misses some
  separated coins:
  - it follows a `SIGHASH_DEMURRAGE` signature only through transactions in
    the wallet, so a coin received from a transaction that descends from one
    elsewhere does not count;
  - it does not recognize the flag in a script-path spend;
  - on a pruned node, it does not recognize the flag in a transaction whose
    block's undo data was pruned.

  The option is set for the node, not for each wallet.
- **External signers** (`-signer`) receive the PSBT fields, but whether they
  can sign with `SIGHASH_DEMURRAGE` depends on their own software.
  `-walletdemurragesighash` does not change how they sign. For them, coin
  selection prefers only separated coins.
- **Proofs for light clients.** Blocks carry the demurrage commitment, but no
  RPC builds a proof of a transaction's reference height against it.
- **The fee at index 1.0** as the mempool's common index: the mempool keeps
  `fee_effective` in the next block instead (see Mempool fees above).

## Known limitations

- The timestamp rules use the network's difficulty adjustment period: 2,016
  blocks on mainnet, 144 on regtest.
- A pruned node upgraded after activation must restart with `-reindex`,
  because the blocks it must validate again are no longer on disk.
- `gettxoutsetinfo`'s `total_amount` and per-block `block_info` amounts remain
  nominal, and nominal totals can exceed 21,000,000 BTC over time.
- `gettransaction` and related RPCs fall back to nominal input values for a
  transaction whose block's undo data has been pruned, and so do the amounts
  received by address for such a transaction. `decodepsbt` and
  `analyzepsbt` omit the fee if a spent coin is not in the UTXO set or the
  mempool.
- Lightning software must report channel balances as effective values (BIP
  462's balance reporting); that is outside Bitcoin Core.
