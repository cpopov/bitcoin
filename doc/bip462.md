# BIP 462 reference implementation: target-based demurrage

This branch is a reference implementation of
[BIP 462 (draft 0.3.0), *Target-Based Demurrage Security Budget*](https://github.com/cpopov/bips/blob/demurrage-security-budget/bip-0462.md).
It is a **hard fork**. It is not scheduled on any network: mainnet, testnet and
signet have no activation height. On regtest it activates only with
`-testactivationheight=demurrage@<height>`.

## Trying it on regtest

```bash
bitcoind -regtest -testactivationheight=demurrage@432 -daemon
bitcoin-cli -regtest createwallet w
bitcoin-cli -regtest -generate 600
bitcoin-cli -regtest getdemurrageinfo
```

Regtest uses `RATE_PERIOD = 144` and a target of 1/500 per block (0.2% per
block, far above mainnet's 0.3% per year). That way demurrage is non-zero
while regtest's fast-halving subsidy (every 150 blocks) still exists.

## Design decisions the BIP leaves open

These are choices this implementation had to make. Each should either be
written into the BIP, or replaced there by a better rule.

1. **Fixed-point representation.** I(h) and r_k are integers scaled by
   10^18 (`INDEX_ONE`). Every operation rounds down:
   - `I(h) = floor(I(h-1) * (10^18 - r) / 10^18)`;
   - `r_k = floor(max(0, target - covered) * 10^18 / (RATE_PERIOD * U_k))`, with
     `target = floor(U_k * RATE_PERIOD * 3 / 52,560,000)`;
   - `effective = floor(v * I(at) / I_created)`;
   - `dividend = floor(r * U / 10^18)`;
   - `payout = floor(pool / 1000)`.

   On mainnet the target rate is 57,077,625,570 (≈ 5.7078e-8 per block).
2. **U(h), the effective value of the UTXO set.** A sum of per-output floors
   cannot be maintained incrementally, because every output's floor changes
   every block. The implementation tracks the exact integer
   `N = sum(floor(v * 10^36 / I_created))` over all unspent outputs, adding and
   removing outputs as blocks connect, and defines `U(h) = floor(N * I(h) / 10^36)`.
3. **U at activation.** All outputs created before activation have
   `I_created = I(ACTIVATION_HEIGHT - 1) = 1`, so `N` at that height is the
   UTXO set's total value × 10^18. The node computes this with a single scan
   of the UTXO set when its tip reaches `ACTIVATION_HEIGHT - 1`.
4. **I_created of pre-activation outputs** is `I(ACTIVATION_HEIGHT - 1) = 1`.
   This matches the activation block's dividend, `r_0 * U(ACTIVATION_HEIGHT - 1)`.
   Rule 1 still treats their reference height as `ACTIVATION_HEIGHT`. The BIP
   says both "the activation height" and `I(ACTIVATION_HEIGHT - 1) = 1`, which
   differ by one block of decay when `r_0 > 0`.
5. **Rate periods** start at `ACTIVATION_HEIGHT + k * RATE_PERIOD`. Subsidy
   and fees are tracked from `ACTIVATION_HEIGHT - RATE_PERIOD` (or height 1).
   `subsidy_{k-1}` is the schedule amount (`GetBlockSubsidy`), whatever the
   coinbases actually claimed. For mainnet, `ACTIVATION_HEIGHT` should be a
   multiple of 2016, so that rate periods coincide with difficulty periods.
6. **Serialization of `ref_height`.** It is serialized in the extended
   transaction format as flag bit `0x02` (bit `0x01` is the witness flag), as a
   4-byte little-endian integer after `nLockTime`. It is non-witness data:
   the marker and flag are written even without witnesses, so the txid commits
   to it. A plain "new version" rule (`nVersion == 4` ⇒ an extra field) would
   misparse historical transactions, because `nVersion` was unconstrained
   before BIP 68. Every flag other than `0x01` used to be rejected, so no
   historical transaction can carry bit `0x02`.
7. **Version coupling.** After activation, a non-coinbase transaction has a
   `ref_height` if and only if its version is at least 4
   (`bad-txns-refheight-version`). A coinbase may not have one. Before
   activation, no transaction may have one (`bad-txns-refheight-premature`).
8. **Signature hashes commit to `ref_height`.** Without this, anyone could
   change a transaction's reference height, which changes the value of its
   inputs, its fee and its txid. The field is appended after `nLockTime` in
   the legacy and BIP 143 digests, and after `nLockTime` in BIP 341's
   `SigMsg`, which grows by 4 bytes.
9. **Coin and undo formats.** A coin whose reference height differs from its
   inclusion height sets bit 32 of its serialized code, followed by
   `VARINT(height - ref_height)`. Undo records keep the delta in the slot that
   old versions used for a transaction version. Existing UTXO sets and undo
   files stay readable.
10. **Underclaimed coinbases.** Value the coinbase does not claim (subsidy,
    pool payout or dividend) is destroyed. It does not return to the pool.
11. **Rounding remainders.** The BIP says rounding remainders "accrue to the
    fee pool". The remainders are fractions of a satoshi, so the
    integer-satoshi pool cannot receive them. They are dropped. Effective
    supply (U + pool) therefore grows by the subsidy minus a few satoshis per
    block: at most about one satoshi per input and per transaction. The
    functional test checks this bound on every block.

## Policy and wallet

- **Legacy-version transactions are not relayed after activation**
  (`demurrage-legacy-version`), although they remain valid in blocks. They are
  valued at their unknown inclusion height, so their fee shrinks, and they can
  become invalid, every block they wait. A mempool cannot hold them
  consistently. Legacy transactions left in the mempool at activation are
  removed. In practice, wallets must create version 4 transactions to be
  relayed.
- **Mempool fees** are `fee(tx)` at the reference height. The pool receives
  `fee_effective`, which is slightly less when a transaction is mined after
  its reference height.
- **Reorgs.** The mempool re-checks reference heights and input values
  against the new chain. Disconnecting the activation block makes reference
  heights invalid again.
- **The wallet**, once BIP 462 applies to the next block, creates version 4
  transactions with `ref_height` set to its last processed block. It selects
  coins at their effective value and reports effective balances (`getbalance`,
  `getbalances`). Amounts in transaction history and `listunspent` remain
  nominal. The fee in `gettransaction` is computed from nominal values, so it
  includes the inputs' decay.

## Known limitations

- assumeutxo snapshots do not carry per-block demurrage state, so a snapshot
  above `ACTIVATION_HEIGHT - RATE_PERIOD` cannot be used.
- A node already past `ACTIVATION_HEIGHT - RATE_PERIOD` when it first runs
  this code needs `-reindex-chainstate`.
- PSBTv2 carries `ref_height` in a provisional global field, key type
  `0x07` (`PSBT_GLOBAL_REF_HEIGHT`), which needs an amendment to BIP 370.
  PSBTv0 carries it in the unsigned transaction, which uses the extended
  serialization when it has a reference height.
- `gettxoutsetinfo`, `scantxoutset`, the coinstats index and the REST
  interface report nominal values. Nominal totals can exceed 21,000,000 BTC
  over time.
- External (non-wallet) inputs passed to wallet RPCs are taken at the value
  given by the caller.
- Lightning-specific behaviour (BIP 462's Layer 2 section) is out of scope.

## Observations on the BIP's economics

- **The fee pool removes the direct incentive to include transactions.** A
  miner with hashrate share `h` eventually receives only `h * F` of a fee `F`
  that it includes, and the rest goes to other miners. Including transactions
  becomes a public good among miners. Their marginal reward for filling a
  block is close to zero, and the case for out-of-band fees, which the BIP
  already discusses, gets stronger.
- **Pre-signed legacy transactions decay in the mempool**, as the BIP says,
  and they cannot be relayed reliably. TRUC (version 3) transactions, which
  current Lightning designs use, cannot carry a reference height, because the
  BIP ties it to a new version. A version-independent flag, such as the
  serialization flag this implementation uses, would let TRUC and
  `ref_height` combine.
